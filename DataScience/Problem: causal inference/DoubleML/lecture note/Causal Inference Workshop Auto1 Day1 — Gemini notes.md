- Merging Machine Learning and Causal Inference: The core goal is to merge the fields of machine learning and causal inference, known as causal machine learning. Machine learning is noted for its success in learning complex patterns and its forecasting power, typically based on correlations and associations (00:15:13). Causal inference focuses on learning causal relationships, moving beyond mere correlations, which is essential for "real intelligence" (00:16:52).

- Causality vs. Prediction and Applications: Predictive modeling aims to build strong prediction rules for an outcome $Y$ based on features $X$, while causal modeling focuses on determining the causal effect of a treatment $D$ on an outcome $Y$ (00:21:08). Causal machine learning is used in various applications, including resource allocation, A/B testing, uplift modeling, dynamic pricing, clinical trials, and product optimization (00:18:20).

- Fundamental Problem of Causal Inference: Causal inference typically begins by defining the causal parameter of interest and stating necessary assumptions for identification and valid estimation (00:25:28). The fundamental problem is that individual causal effects cannot be generally identified because only one potential outcome (the factual) is observed, while the other (the counterfactual) is not (00:32:46).

- Identification vs. Estimation: The process of causal inference moves from a hypothetical causal estimate to a statistical estimate, then to a modeling estimator, and finally to a statistical estimate that provides actionable insights (00:26:55). The core challenge, identification, is about ensuring that the assumptions are plausible so that observations in the data can be generalized to hypothetical quantities (00:28:24).

- Potential Outcomes and Average Treatment Effects (ATE): Using uplift modeling (email coupons' effect on sales) as an example, the binary treatment $D$ leads to two potential outcomes, $Y(1)$ and $Y(0)$, for a treated and untreated subscriber (00:31:01). While the individual causal effect $Y(1) - Y(0)$ is unidentifiable, the Average Treatment Effect (ATE) can often be identified, which is the difference in expected outcomes if everyone were treated versus if no one were treated (00:32:46).

- Randomized Control Trials (RCTs) and Observational Data: In an ideal RCT, treatment assignment is randomized and independent of potential outcomes, allowing the ATE to be consistently estimated by comparing the observed outcomes of the treatment and control groups (00:34:19). However, when RCTs

are not possible due to constraints, observational data is used, necessitating the "selection on observables" (unconfoundedness) assumption to estimate causal effects (00:37:28).

- Addressing Confounding in Observational Data: With observational data, treatment assignment is not random, and confounding factors $X$ influence both the treatment $D$ and the outcome $Y$. The unconfoundedness assumption posits that if they condition on a rich set of observed covariates $X$, the treatment becomes "as good as random," allowing for an apples-to-apples comparison of individuals with similar characteristics (00:39:00) (00:44:27).

- Initial Causal Estimation Methods: Methods for causal estimation when controlling for confounders include regression adjustment, reweighting approaches using inverse propensity scores, and doubly robust methods that combine both (00:44:27). Simple linear regression can be used for causal estimation, but it requires strong assumptions like linearity and an additive model, in addition to correctly identifying the variables to condition on (00:40:19).

- Need for Double Machine Learning (DML): When dealing with high-dimensional problems, machine learning methods are needed because linear regression performs poorly, and regularization techniques like Lasso introduce bias into the treatment effect estimates (00:43:08) (00:47:21). DML is necessary to leverage the predictive power of machine learning algorithms while maintaining valid inference in the presence of regularization (00:47:21) (00:49:47).

- Machine Learning for Causal Inference: Machine learning methods are powerful for modeling the complex relationships between the outcome $Y$, the treatment $D$, and the covariates $X$, moving beyond the limitations of simple linear regression (00:49:47). There was a discussion regarding the importance of selecting the correct variables to control for, as improperly controlling for variables can downgrade performance (00:51:06).

- Double Machine Learning Framework: Double machine learning merges modern predictive algorithms (like Lasso, Random Forest, or boosting methods) with the robust inferential tools of econometrics and statistics (00:52:31). This framework aims to achieve high predictive power and valid inference, where the predictive power of the machine learning methods is what matters for the asymptotics of the point estimate (00:56:27).

- Nuisance Functions and Causal Estimation Bias: Nuisance functions, defined as outcome regression (conditional expectation of outcome given features) and

propensity score estimates (probability of treatment given covariates), are typically estimated using machine learning, but plugging these predictions directly into the treatment effect estimation introduces bias. Machine learning methods utilize regularization (e.g., penalization or early stopping) to optimize for prediction accuracy, which introduces regularization bias into the nuisance estimates, consequently propagating to the causal estimate, rendering the naive approach ineffective (00:58:44). Small errors in nuisance estimates can lead to substantial bias in the causal estimate, which invalidates standard inference methods such as confidence intervals and p-values (01:00:08).

- Neyman Orthogonality for Bias Reduction: A framework is needed to immunize the causal estimate against regularization bias, and the first key ingredient of Double Machine Learning (DML) is Neyman orthogonality, which constructs score functions such that errors in nuisance functions only have second-order effects on the causal estimates (01:00:08). The geometric intuition is that the estimation error in the nuisance direction (horizontal axis) does not change the position of the causal parameter (vertical axis) because they are set up to be orthogonal to each other. The double machine learning package automatically uses orthogonal scores, but they must be derived when extending the package with new models (01:02:48).

- High-Quality Machine Learning Estimation: The second ingredient for DML is the requirement for high-quality machine learning estimation, as orthogonality only reduces bias to some degree, meaning nuisance errors cannot be arbitrarily large. The product of machine learning errors from the different nuisance components (outcome regression and propensity score estimation) must still shrink fast enough. Practical guidance suggests using flexible learners appropriate for the data and performing proper hyperparameter tuning for nuisance functions, as the impact of tuning is substantial (01:04:34).

- Sample Splitting and Cross-fitting: The third DML ingredient is sample splitting, which prevents overfitting done during training from contaminating the causal estimates by ensuring that overfitting errors are not correlated with estimation errors. The implementation solution is cross-fitting, where data is split into $K$ folds (e.g., five), and for each fold, machine learning methods are trained on the other folds to make held-out predictions (01:07:38). The benefits of cross-fitting are that predictions are always out-of-sample, and all data is used for both training and estimation, which is more efficient than a simple train-test split (01:09:05).

- Main Result and Implementation Overview: When combining the key ingredients—Neyman orthogonality, high-quality machine learning estimation, and sample splitting—the DML estimator is consistent, and the sampling error is approximately normally distributed, which enables valid inference and the construction of standard errors and confidence intervals (01:10:19). The package implementation is object-oriented, exploiting a common structure around score functions, which facilitates flexibility in combining data and models (01:11:54). The package is built to easily use state-of-the-art machine learning predictions and tuning methods for nuisance components, utilizing a similar API to scikit-learn, and the default setting for sample splitting is five-fold cross-fitting (01:13:09).

- Implemented Model Types: The DML package has a constantly growing list of implemented models, including the general class of partially linear models, nonparametric interactive regression models, potential outcome models, instrumental variables, and recently added difference in differences, sample selection, and regression discontinuity (01:14:25) (01:24:59). The models support various causal estimates, such as average treatment effect, conditional average treatment effect (CATEs), and group average treatment effects (01:15:50). Martin Bierey asked if group average treatment effects require predefined groups, and Sven Klaassen clarified that most implementations rely on predefined groups, although some methods may attempt to find groups using tree-based approaches (01:23:29).

- Treatment and Outcome Restrictions: Tsz Yan Lam inquired about restrictions on the outcome type (continuous or binary) for the implemented models. Sven Klaassen noted that most models are applicable to either binary or continuous outcomes, but all settings assume a single outcome, not a multivariate one (01:18:27). For the partially linear model with a binary outcome, a logistic version is implemented, as an additive probability model may not be appropriate, suggesting that nearly all models should accommodate continuous or binary outcomes (01:19:33).

- Handling Binary Outcome Residuals: Tsz Yan Lam asked how residuals are defined in the case of a binary outcome (0 or 1), given that standard residual-on-residual regression relies on a continuous target (01:19:33). Sven Klaassen explained that the residual-on-residual intuition comes from the orthogonality assumption in the partially linear regression model, which relies on an additive structure (01:20:44). For binary outcomes, the logistic version or a

completely interactive model is often more appropriate, and in those cases, the method changes to a plug-in score function rather than residual-on-residual regression, maintaining the orthogonality property (01:22:13).

- Typical DML Workflow Steps: The typical DML workflow starts with problem formulation, including drawing a dependence graph (DAG) to visualize available and unobservable features, which helps in interpreting and getting a feeling for the problem (01:40:43). Next, users define data objects by specifying the outcome (Y), treatment (D), and conditioning variables (X) (01:43:36). The third step is model selection, where users choose an appropriate DML model (e.g., partially linear, interactive regression) based on the desired estimand and data structure (01:45:03).

- Defining Machine Learning Estimators: The fourth step in the DML workflow is defining the machine learning methods (learners) to be used for the nuisance functions, which must follow the scikit-learn API style with fit and predict methods (01:45:03). Users must choose one model for the outcome regression (G) and one model for the treatment regression/classification (M), where the choice depends on the outcome and treatment types (01:47:39). Daniel Jacob asked about consistency between the outcome and treatment regressors and Sven Klaassen clarified that in their implementation, one feature vector (X) is typically used for both regressions (01:50:20).

- Hyperparameter Tuning and Prediction Accuracy: The final steps in the workflow involve using the `tune_models` method to perform hyperparameter tuning to achieve the best cross-fitted predictive performance for both the treatment and outcome predictions (01:55:37). Martin Bierey asked about accuracy goals for both models, and Sven Klaassen confirmed that the aim for both models is high predictive accuracy, noting that for the outcome model, the treatment variable should often be included in the regression (01:54:31). Tsz Yan Lam confirmed that models without a scikit-learn interface could be wrapped around with the required fit and predict functions, or external predictions could be used in complex cases (01:49:13).

- API Integration and Model Fitting: The discussion focused on running models with an API design that is close to the scikit-learn (sklearn) style, where the process involves setting up the learner and problem, and then using a `fit` method. The `fit` method internally handles cross-fitting and runs machine learning models after hyperparameter setting, resulting in a final point estimate and standard errors. The point estimate for a random forest example was 8.135,

noting that standard errors in these problems are typically large due to measurement noise (01:56:56).

- Predictive Performance and Model Summaries: The main idea is that the predictive performance of the models should matter in the background to estimate conditional expectations or probabilities that solve the underlying problems. Models that perform well yield predictions that are close to each other, resulting in very close final point estimates. The final object includes a summary detailing the number of observations used, the type of machine learning algorithm, and the corresponding out-of-sample performance (01:58:27).

- Confidence Intervals and Evaluation Options: The object summary provides standard statistical outputs, including standard errors, t-values, p-values, and confidence intervals (CIs). Users can create CIs at different levels, which are calculated via a normal approximation within the framework (01:59:55). It is also possible to include jointly valid CIs using a bootstrapping procedure for scenarios with multiple treatment effect estimates (02:01:10).

- Hyperparameter Tuning with Optuna: A recent addition to the package is the integration of the Optuna tuning framework, which is flexible and customizable (02:01:10). The user's main task is to achieve good predictive performance, as the cross-fitting and score orthogonality are already implemented in the model. Tuning is crucial because default settings, such as those sometimes found in sklearn's random forest, can lead to overfitting, making hyperparameter selection relevant to minimize nuisance errors and improve generalization (02:02:29).

- Defining Hyperparameter Search Space: To perform hyperparameter tuning with Optuna, users must define `trial` objects, which specify the ranges for hyperparameters to be tested. This involves defining a function that returns a dictionary matching the desired hyperparameters (02:04:09). The search spaces, which can include floating, integer, or categorical values, must be defined separately for treatment and outcome regression, though they can be reused if identical (02:05:42).

- Optimization Process and Model Comparison: The `tune_models` method is run with defined hyperparameter spaces and settings, such as the number of trials. Optuna employs an optimization process that samples hyperparameter configurations, balancing exploration with sampling near good combinations, which is more optimized than random grid search (02:07:59). A comparison between an untuned and tuned LightGBM model showed the estimate changing

drastically (from 0.06 to 0.5), with the tuned model yielding a much smaller standard error, demonstrating the impact of tuning (02:10:36) (02:19:16).

- S-Learner vs. T-Learner Structures: The framework uses a T-learner structure for interactive regression, which fits two separate outcome regressions: one for the treatment group and one for the control group (02:10:36). A T-learner is considered more flexible than an S-learner (single regression including treatment as a feature), as it is equivalent to including all interaction terms between treatment and features (02:11:55) (02:15:26). The framework fits these two models separately by cloning the outcome regression model, which allows for potentially different hyperparameter combinations to address issues like unbalanced treatment assignment (02:13:03).

- Derivation of Standard Errors: Standard errors are derived using a Wald-type approach based on the score function and an asymptotic representation of the estimator (02:20:41). Specifically, the computation involves calculating the second moment of the scores empirically along with a necessary scaling factor (02:21:51). Testing has shown that the coverage for these standard errors performs well (02:23:12).

- Evaluating Learner Performance: The `evaluate_learners` method allows users to assess the cross-fitted performance of the learner using metrics like root mean square error (RMSE) for continuous variables or log loss for binary variables (02:23:12). Out-of-sample performance metrics improved significantly after tuning, explaining why the causal effect estimation was better (02:24:27).

- Using Scikit-learn Pipelines: The package supports the use of scikit-learn pipelines, allowing users to combine multiple regressors (e.g., linear regression and boosting) and incorporate steps like robust scaling before model fitting (02:24:27). This pipeline structure works within the tuning framework, enabling the separate tuning of components, which is helpful for creating robust estimations by combining different types of models (02:27:07).

- Accessing Detailed Tuning Results: Users must set a flag to return detailed tuning results, which go beyond modifying the object with optimal hyperparameters. The results object contains specific tuning results for each regression (e.g., outcome control, outcome treated, and propensity score), including the best score achieved, chosen parameters, and individual trial data (02:28:30).

- Feature Transformation and External Integration: The discussion touched upon complex feature transformations, such as the target encoding used by CatBoost, and their integration into the package (02:31:35). While it may not be straightforward if the transformation does not fit the standard pipeline structure, users can generate predictions externally and supply them to the model, treating the external estimate as if it were computed internally (02:34:47).
